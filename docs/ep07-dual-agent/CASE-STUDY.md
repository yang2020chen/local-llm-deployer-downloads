# 案例复盘｜两个 AI 做 Windows 软件，为什么不断被打回？

> 玩客笔记 EP07 视频配套。下述内容依据作者私有交接仓库的 Issue #16、#21、#24 及关联开发 PR #2、#7、#9 整理，**是脱敏事件摘要，不是 GitHub 原始页面截图或逐字完整档案**。
>
> 这不是一项新的复现实验。涉及 Windows 实机测试的部分，仅按照既有本地执行报告陈述，不宣称由本文编写者重新进行了测试。

## 故事背景

目标是在真实 Windows + RTX 3060 等硬件上，制作普通用户可以下载、安装并启动本地大模型的图形化工具。合作方式是：

- **ChatGPT**：规划任务、定义验收、审核本地 Agent 的 PR 和证据。
- **Antigravity / 本地 Agent**：在实际 Windows 工作区写代码、编译、测试、回报。
- **GitHub Issue / PR**：保存需求、差异、审查记录。
- **用户**：决定范围例外、合并、打包和最终发布。

三个事件的共同结论是：**通过自动化检查不等于可以发布；证据必须覆盖原目标，人类仍保留最终批准权。**

## 案例一：Issue #16 — 安装包能运行，但许可证漏随包交付

**当时的任务**：制作面向普通用户的 Windows 安装器，自动准备兼容推理后端与模型下载流程。执行端为关联 PR #2 提交了安装包及本地测试结果。

**冲突**：云端复核在安装器交付中发现，相关第三方许可证和 NOTICE **没有完整随最终安装包交付**。仓库里存在 LICENSE 文件，不等于打包脚本把它放进用户安装目录。云端在一次限定修复后的复验给出 `BLOCKED`，没有因为软件可运行而放行。

**如何收束**：用户给予一次**明确的范围例外授权**，只允许补充正确的上游 LICENSE/NOTICE 并核对安装交付，不顺手加功能。本地修正回报后，云端再按原验收范围复审并给出 PASS。

**教训**：安装器、软件依赖和许可告知是一个交付整体；“代码仓库里有文件”和“用户拿到的安装包里有文件”是两件事。具体分发义务取决于实际第三方组件的许可证条件，不应将这一案例简化为所有遗漏都自动构成既定法律结论。

**材料来源（私有，公众不保证可打开）**：Issue #16 审核评论标识 `#6233744714`（BLOCKED）、用户特别授权 `#6233760854`、复核 `#6233881928`；关联 PR #2。

## 案例二：Issue #21 — curl 返回 200，仍不等于网页聊天可用

**当时的任务**：为客户端增加默认关闭、需要显式授权的局域网网页访问功能。执行端通过 PR #7 提交代码和验证记录。

**冲突**：执行端曾以 HTTP 请求成功作为浏览器验收充分证据。但 `curl` 能证明接口响应，却不能单凭 `HTTP 200` 证明浏览器实际执行 JS、渲染 DOM、完成聊天交互。云端指出原验收尚未被证明，在复核中标记 `BLOCKED`，而不是把接口测试冒充浏览器端到端测试。

**如何收束**：在用户额外批准的范围内，本地执行端补充 Mac 上真实 Chrome 浏览器的跨机验证，检查页面脚本加载、输入提交和聊天结果显示；既有执行记录报告了 `LAN-BROWSER-OK` 的界面/DOM 证据。云端复核确认代码与提供的证据符合本轮代码阶段要求，并明确区分远端证据与自己未亲自运行的 Windows/Mac 操作。

**教训**：测试名称与实际测试行为必须一致。网络连通性、浏览器前端和模型回复属于不同层次；缺任何一层都不能笼统写“网页实测通过”。

**材料来源（私有）**：Issue #21 评论标识 `#6246887117`（BLOCKED）、`#6248795950`（额外授权下的执行端回报）、`#6248832169`（代码阶段 PASS）；关联 PR #7。

## 案例三：Issue #24 — 剪贴板闪退与“修复越界”

**当时的问题**：Windows 客户端复制地址等操作曾出现 `COMException 0x800401D0 / CLIPBRD_E_CANT_OPEN`，需要最小热修复。

**第一次修复为何被打回**：本地 Agent 的 PR #9 引入了剪贴板重试服务，但代码审核同时发现了与任务无关的旧测试清理代码 `try/catch` 包裹，还发现对宽泛 `ExternalException` 的重试可能误吞非剪贴板占用的异常。审核要求**还原无关改动，限定重试对象，补一项真实 Windows UI 复制操作证据**。

**修复结果**：后续版本只对错误码 `0x800401D0` 的可恢复剪贴板占用进行**最多 3 次尝试**（两次等待约 50/100ms）；其它异常立即安全失败。执行端报告 Windows 单元测试 `124/124 PASS`，并提供真实界面复制按钮的冒烟记录；云端核查 PR diff，明确注明硬件 UI 互动仍由本地执行端报告支持。

**最重要的停手时刻**：那次**代码审核通过时**，审核记录仍写着：

```yaml
task: 24
review: PASS
unit_tests: 124_PASS_LOCAL_REPORTED
installer: NOT_BUILT
pr_merge: NOT_AUTHORIZED
v1_3_1_release: NOT_AUTHORIZED
```

这代表：**在当时的审核阶段，AI 并没有合并、重新打包或发布的授权。** 后来用户单独批准，PR #9 才合并并完成 V1.3.1 打包与发布，不能把历史“等待审批”的画面说成今天仍未合并。

**材料来源（私有）**：Issue #24 审查评论标识 `#6259026930`（FIX）、`#6259314888`（仅代码阶段 PASS）、后续单独授权与发布记录；关联 PR #9。

## 对三次事件的统一总结

| 事件 | 表面上的“已完成” | 实际缺口 | 正确的收束方式 |
| --- | --- | --- | --- |
| 安装包 | 可安装、测试过 | 上游许可/NOTICE 未随包交付 | 定点修正后核对安装产物 |
| LAN 网页 | 请求返回 HTTP 200 | 缺少真实浏览器执行与聊天证据 | 用户授权后补 Chrome 端到端核验 |
| 剪贴板 | 代码修复、单测通过 | 宽泛异常/无关改动与真实 UI 证据 | 最小修改、独立审核、人工批准发版 |

**一句话：AI 可以写代码，可信交付需要清楚的任务边界、真实证据和最后的人类裁决。**
